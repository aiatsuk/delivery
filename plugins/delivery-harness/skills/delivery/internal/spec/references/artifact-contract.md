## Where packages live

The delivery coordinator passes `--root <run>/spec` to every engine command. This explicit path
always wins over environment variables, project discovery, and repository configuration. The
package stays with the run's evidence outside the project.

Direct engine use retains the source engine's optional machine-store API: `$SPEC_FLOW_HOME`,
then `$XDG_STATE_HOME/spec-driven-development`, then `~/.local/state/spec-driven-development`.
Within that store, Git common-directory identity groups a primary checkout and its linked
worktrees under one `<project-name>-<identity-digest>/{changes,checks}/<slug>/` entry. Non-Git
projects use resolved directory identity. These compatibility commands do not create or choose
a separate delivery run. `verification.artifact_store: repo` is an explicit standalone opt-in;
the coordinator's `--root` still takes precedence.

## Standard package

Before approval, create:

```text
spec-session.json
intent.md
feature-model.md
proposal.md
decisions.md
specs/<capability>/spec.md
design.md
impact-analysis.md
verification-cases.md
test-plan.md | evaluation-plan.md
tasks.md
review.md
review-brief.md
```

After implementation, add:

```text
implementation-evidence.md
actual-diff.json
post-implementation-review.md
verification-report.md
```

The delivery coordinator decides whether this full semantic package is needed. This engine does
not impose its planning artifacts on a trivial delivery. Once a semantic package is selected,
high-risk work may add security, privacy, migration, rollout, or operational artifacts without
removing its baseline gates.

## Check package

A check package uses the explicit directory selected by the delivery coordinator:

```text
spec-session.json          mode: check, depth mode, recorded risk passes, authorization
source.md                  every source verbatim, resolved inputs, reference documents
actual-diff.json           change inventory, when a diff is available
impact-map.md              changed, affected, and indirect surface plus protected invariants
check.json                 machine-readable risks, cases, environment, questions, waivers
verification-cases.md      generated detailed cases
verification-brief.md      generated single human-facing output
case-review.md             independent audit of the cases
verification-report.md     added only after authorized execution
```

`check.json` is the single source of truth. `verification-cases.md` and `verification-brief.md`
are generated by `check-render`; editing them by hand desynchronizes coverage and readiness from
the validated data. Present the brief to the user, not the internal artifacts.

## Ownership and traceability

- `intent.md` owns exact source wording, normalized intent, constraints, non-goals, unknowns, and a
  fidelity map. Never replace the raw input with a summary.
- `feature-model.md` owns L0-L7 decomposition and parent-child links.
- `decisions.md` owns material ambiguity, options, recommendation, owner, state, and affected IDs.
- `specs/` owns observable behavior with stable requirement/scenario IDs.
- `design.md` satisfies accepted behavior without adding product decisions.
- `impact-analysis.md` owns consequence hypotheses and protected invariants.
- `verification-cases.md` owns reproducible checks and authoritative oracles.
- `tasks.md` owns dependency order and links every task to requirements, risks, or tests.
- `review.md` owns cross-artifact consistency and readiness findings.
- `review-brief.md` is a compact synthesis, not a replacement for detailed artifacts.

Every downstream capability, task, risk, and test must trace to accepted intent or an explicit
decision. Orphans are findings, not harmless documentation gaps.

## L0-L7 feature model

Give nodes stable IDs and link each child to its parent. Expand a node only if decomposition reduces
uncertainty, separates responsibilities, exposes a dependency, or creates an objective oracle.
Stop when one responsibility has an observable result, known dependencies, an oracle, and no
hidden material decision.

## Template use

`assets/` contains the canonical templates. Copy and fill them without deleting headings that
represent required evidence. Remove instructional placeholder text from final artifacts. Add a
capability spec under `specs/<capability>/spec.md`; the example `assets/spec.template.md` is not a
valid substitute at the package root. From the engine directory, run
`scripts/spec_flow.py validate --root <change-dir>`
before review; an existing filename with template placeholders is incomplete evidence.
